# ARCHITECTURE — Mandate (as built)

> What exists in this repository, in the order an engineer would read it. Diagrams
> live in `docs/UML.md`; the claims live in `docs/CLAIMS.md`. Anything described
> here can be pointed at a file.

---

## 1. Shape

One Rust contract, one static console, one deterministic replay, four Node tools.
No server-side rendering, no database, no key material in the repository, no
network call at runtime.

```
mandate/
  contracts/mandate/src/
    lib.rs        the contract: owner paths, agent path, views
    state.rs      stored types and the JSON return types
    policy.rs     the policy object, its hash, its validation
    errors.rs     PolicyViolation + the frozen code list
    util.rs       sha256, intent_hash, storage helpers
    tests.rs      27 unit tests, one per failure path plus the happy paths
    demo.rs       the fifteen-event scenario (writes the snapshot)
  console/
    index.html    shell: context bar, tabs, canvas, proof rail
    styles.css    the whole visual system (tokens at the top)
    app.js        reads snapshot.json + docs.json; renders; recomputes hashes
    data/
      snapshot.json   committed replay (generated by make demo)
      docs.json       generated from markdown by make docs
  docs/
    SCREENER.md   the hostile-reviewer path
    ARCHITECTURE.md  this file
```

Everything under `tools/` is dependency-free Node: `serve-console.mjs`,
`demo-report.mjs`, `verify.mjs`, `doctor.mjs`, `build-docs.mjs`.

## 2. Contract surface

| Path | Caller | Effect |
|---|---|---|
| `new(attestor)` | deployer | owner = predecessor, stores the attestor account |
| `create_mandate(agent, policy)` payable | owner | balance = deposit; policy hash; revision 1 |
| `fund(id)` payable | owner | adds to the balance |
| `suspend(id)` / `resume(id)` | owner | the kill switch, a flag |
| `update_policy(id, policy)` | owner | new hash, revision + 1, history append |
| `spend(id, chain, amount, asset, vendor, attestation)` | agent | the whole check order, then debit or escalate |
| `approve(request_id)` / `reject(request_id)` | owner | answers a stored escalation |
| `settle(id, intent, tx_ref)` | attestor | records the foreign tx once |
| `get_mandate`, `list_mandates` | anyone | mandate views |
| `list_pending`, `get_pending` | anyone | the escalation queue |
| `get_settlement`, `get_policy_history` | anyone | settlement and revisions |
| `stats`, `held` | anyone | counters and the total the contract holds |

The UI never computes money: every figure it prints is a field from one of those
views. `held()` exists so the console can show custody without summing in JS.

Every refusal logs `violation: <code>` before it panics (D-018). The release
profile uses `panic = "abort"`, so an on-chain failure arrives as a wasm
`unreachable` trap with no message; the log line is what lets a stranger read the
typed code in the block explorer instead of taking our word for it.

## 3. Data and invariants

State: `owner`, `attestor`, `mandates: BTreeMap<id, Mandate>`,
`pending: BTreeMap<request_id, PendingRequest>`,
`used_decisions: BTreeMap<decision_hash, bool>`, `next_id: u64`.

Invariants, each with a test:

1. `balance + spent_total == deposit_total` for every mandate.
2. `policy_rev == policy_history.len()`.
3. `policy_history.last().hash == policy_hash`.
4. A decision hash appears at most once in `used_decisions`.
5. `spent_day + value <= per_day` and `spent_by_counterparty[k] + value <=
   per_counterparty_day` after every authorised spend.
6. A settlement exists at most once per `(mandate, intent)`.

The day window is `block_timestamp / 86_400_000`. On rollover, `spent_day` resets
and the per-counterparty map is cleared. That is correct for the limits and is
listed as a limitation in the whitepaper: history is not retained per day.

---

## 4. Check order

```
suspended → expired → asset → chain → vendor → amount>0 → per_tx →
day rollover → per_day → per_counterparty → balance → attestation
(present → code hash → policy revision → decision unused → intent match) →
escalate or debit
```

The order is deliberate: the cheapest and most legible refusals come first, and
the attestation checks come last so a bad amount is reported as an amount
problem, not as an attestation problem. `docs/UML.md` §7 draws this.

Two families of code are easy to confuse:

- `attestation_mismatch` — same revision, but the intent the enclave decided on is
  not the intent being asked for (amount, vendor, chain, asset).
- `policy_changed` — the decision is internally consistent, but it was made under
  a policy revision that is no longer current.

## 5. Hashing

`policy.hash()` is SHA-256 over `serde_json::to_string(&policy)`. Field order is
fixed by the struct, `U128` serialises as a decimal string, so the byte sequence
is reproducible in Rust, Node and the browser. `tools/verify.mjs` and
`app.js#renderVerify` both recompute it from `policyJson` in the snapshot.

`intent_hash(chain, amount, vendor, asset)` is SHA-256 over
`{"amount":"…","asset":"…","chain":"…","vendor":"…"}` — sorted keys, so JSON
key order cannot change the digest.

The attestor, not the contract, is responsible for the quote hash. The contract
compares a hash; it does not verify Intel's signature. Every document repeats
that sentence because the difference matters.

---

## 6. Determinism

`demo.rs` fixes block height (4 120 001…4 120 016) and timestamp
(1 700 000 000 000 000 000), uses integer amounts, and never reads the wall clock
or a random source. The snapshot therefore hashes identically on every machine;
`make demo` prints the hash, and a change means something non-deterministic
entered the scenario.

The release test also asserts the refusal codes it expects: a scenario that
silently starts succeeding fails the demo instead of recording a misleading step.

## 7. Console

`app.js` fetches two documents: `data/snapshot.json` (contract views per event)
and `data/docs.json` (markdown rendered at build time by `tools/build-docs.mjs`).
It renders six routes from them; it has no other data source.

- `#/desk` — the replay: strip, event card, timeline, mandate table, queue.
- `#/mandate` — limits, allowlist, policy revisions, attestation, settlement.
- `#/verify` — recomputes policy and intent hashes and the revision invariants.
- `#/refusals` — the frozen vocabulary, marking which codes the run produced.
- `#/paper` — whitepaper, architecture and diagrams, from the same markdown the
  repository ships.
- `#/about` — scope, non-claims, keyboard map.

The proof rail is a four-cell record of one event's lifecycle: policy → attest →
authorise → settle. A cell stays empty when its stage did not happen; that is the
point of having four cells instead of a single "success" badge.

Accessibility is a gate, not a courtesy: `axe` runs on every route with the
WCAG 2.0/2.1/2.2 A and AA tags, focus rings are measured, the rail collapses
below 960px, nothing scrolls sideways at 380px, and reduced motion turns the
replay into a jump to the end.

## 8. Tools

| Tool | Contract it keeps |
|---|---|
| `serve-console.mjs` | serves `console/` with `Cache-Control: no-store`; `/health` for readiness |
| `demo-report.mjs` | prints the expected table *before* comparing; fails on one mismatch |
| `verify.mjs` | recomputes 13 checks from the snapshot, prints a stable `inputsHash` |
| `doctor.mjs` | ACTIVE / FALLBACK per module, exits 1 on any fallback |
| `build-docs.mjs` | markdown → `docs.json`; escapes everything, no HTML passthrough |
| `render-diagrams.mjs` | Mermaid → committed SVG; the only tool that uses a package, and not on the `make dev` path |
| `verify-lib.mjs` | the 13 checks, once, shared by `verify.mjs`, the API and the MCP server |
| `api.mjs` | the read model: formats snapshot fields, adds no money |
| `api-server.mjs` | scoped bearer keys, typed JSON errors, read-only |
| `keystore.mjs` / `keys.mjs` | SHA-256 key store and its CLI; the secret is printed once |
| `mcp-server.mjs` | the six read-only tools over JSON-RPC on stdio |

None of the first five need `npm install`. Playwright is used only by `make e2e`,
and `render-diagrams.mjs` needs Mermaid as well; both are development steps, and
their outputs (screenshots, SVG) are committed so a fresh clone renders the same
page.

## 8.1 The control plane (HTTP and MCP)

The console is one client of the snapshot, not the owner of it. Two more clients
are in this repository, both read-only, both behind a scope check:

- `tools/api-server.mjs` — `GET /v1/{status,mandates,pending,stats,policy}`
  (`read:views`), `/v1/events[/:index]` (`read:events`), `/v1/verify`
  (`read:verify`). A bearer key is required; `401` distinguishes
  `unauthorized` from `key_revoked`, `403` is `scope_missing`, `405` refuses
  every non-GET, and `/health` is the only unauthenticated route.
- `tools/mcp-server.mjs` — the same views as six MCP tools over stdio. No
  network, no dependency, no key: it runs where the repository is.

Keys live in `mandate/console/data/api-keys.json` (gitignored): id, label,
scopes, prefix, SHA-256 of the secret, revoked flag. A fresh clone has no file
and therefore no clients, which is why `make test-api` mints its own keys in a
temporary store. Rate limiting is per key, in memory, and the API holds no
signer: there is no code path from either surface to a transaction.

### The original plan, for reference


1. Fund a testnet account, add a FunctionCall key scoped to
   `mandate.testnet::spend`.
2. `cargo near deploy` (or `near deploy` with the release wasm).
3. `create_mandate` with a small deposit; record the transaction id.
4. Set `MANDATE_CONTRACT`; `make doctor` flips the deployment row to ACTIVE.
5. Put the explorer links in `SCREENER.md` §0. The console build line stays a
   replay statement (`replay of a contract run, not a chain read`) because the
   console still renders the snapshot; the deployed account and its transactions
   are rendered from `console/data/chain.json` on the Verify page, so the two
   claims never borrow each other's authority.

Until step 4 happens, every surface says replay and the build line says never
deployed, and `make doctor` exits 1. That is intentional: a green doctor or a
live-looking build line with no deployment would be a lie.

## 10. Extension points

- **Multiple assets per mandate** — policy carries one asset in v1; the balance
  and counters are already per-mandate, so this is a policy shape change.
- **Attestor quorum** — `settle` is a single-account call; a threshold set is the
  natural next step and changes one function.
- **Revocation by key deletion** — the account-level kill switch is outside the
  contract; the contract's `suspend` is the in-band equivalent and needs no key
  operation.
- **Bond** — the deferred second submission (D-011) shares the policy and
  attestation types, not the code: copy, never import (D-004).
