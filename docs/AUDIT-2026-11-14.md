# Audit — 2026-11-14

A hostile-reader pass over both submissions, run before the videos were locked. Two
artefacts came out of it: this file (what was checked, what was found, what was fixed) and
`AUDIT-BRIEF.md` (the same pass written as a prompt, so Grok 4.7 and Kimi 3.1 can run it
independently and their findings can be diffed against these).

**How this pass was run.** By reading the published trees as a judge would — the README
first, then `JUDGE.md`, then the files those two name — and by executing the commands they
tell a judge to run. Nothing was taken on trust from an earlier session; every hash was
re-checked against a public RPC with `tools/check-evidence.mjs`.

**What this pass is not.** It is not an external audit, and it is not a second pair of
eyes: the same author wrote the code it reviews, which is exactly the failure mode a
review is meant to catch. Where a finding rests on the author's reading alone, it says so.

## F-4 — four of the three "clicked not claimed" transactions did not exist (Critical, fixed)

`publish/baseline/JUDGE.md` opened with a table headed *"Three transactions, clicked not
claimed"* and gave four hashes. None of them resolved:

```
MISSING  3aqb32W9Hm…   unauthorized spend (C27)
MISSING  4vGSHH9oj7…   contest / second contest refused (C26)
MISSING  G1JZHxASLm…   the pre-fix spend that was wrongly authorised
MISSING  E8cYASoLZa…   the post-fix spend that was refused
```

The cause was already known and already fixed in the tooling (`tools/near-tx.mjs` now
records the node's canonical `transaction.hash` instead of a locally computed id), but the
hand-written judge file was never re-run through the verifier, so it kept the ids the old
tool produced. In a `security` submission, a judge file whose first table is four dead
links is worse than a judge file with one honest transaction.

**Fixed** by rewriting the table with hashes taken from the dataset and re-verified:
`Ed1DsVvZ…` (allowed spend), `7n6KhL91…` → `4idQpYLo…` (the day ceiling binding after the
fix), `CrC1hiXX…` → `Awq7ureY…` (the counterparty ceiling), `CZmTWZb8…` → `GewJX6kg…`
(suspension). The pre-fix transaction is no longer presented as a hash at all, because the
id we have for it was computed locally; what survives is the contract view it left, which
is what F-1 of the baseline repository's FINDINGS file quotes.

**Detection that should have caught this earlier, and now does:**
`node tools/check-evidence.mjs JUDGE.md` from either published tree. Run it before every
push; it exits non-zero on a single dead hash.

## F-5 — a withdrawn claim was still advertised (High, fixed)

`publish/baseline/JUDGE.md` listed *"A settled payment is contested, the amount returns, a
second contest is refused"* as one of the three proof transactions, and `publish/mandate`
still carried the contest window in its headline, its run-it block and `docs/CLAIMS.md`
C26. `tools/contest-demo.mjs` fails its own assertion, so C26 was withdrawn on 2026-11-13 —
but the withdrawal only reached `docs/EVIDENCE-CHECK.md` and one judge file, not the
copies a judge actually reads.

Worse, re-reading `contest` in `mandate/contracts/mandate/src/lib.rs` against its own
documentation found the reason the demo cannot pass:

```rust
mandate.balance += amount;
mandate.spent_total = mandate.spent_total.saturating_sub(amount);
mandate.spent_day   = mandate.spent_day.saturating_sub(amount);   // ← this line
```

`publish/mandate/README.md` says *"the daily and per-counterparty counters are **not**
rewound — a contested payment still consumed that day's allowance, which is what stops a
contest loop from refilling a ceiling"*. The deployed contract rewinds `spent_day`. Two
consequences: the documentation is false, and — same day, same mandate — `spend → contest →
spend → contest` refills the daily ceiling without limit, which is the exact loop the
sentence claims to prevent. The per-counterparty counter, by contrast, is **not** rewound,
so the two counters also disagree with each other.

**Why it is documented rather than patched in the contract.** Rebuilding the wasm needs
Docker and a Linux toolchain; this machine has neither running (D-008), and the deployed
build is what every hash in these repositories points at. Editing the source without a
redeploy would leave source and wasm describing different contracts — the failure mode
`AGENTS.md` §4 is written against. So the line stays in the source, is named here, and
`docs/DECISIONS.md` D-026 records the fix for the next deploy that has a toolchain.

**Fixed in the copy a judge reads:** C26 is withdrawn in `docs/CLAIMS.md`, the contest
mechanism is described in both READMEs with the defect stated beside it, and the
`make contest-demo` line is gone from the run-it blocks until the demo passes again.

## F-7 — the baseline judge view had no test (Medium, fixed)

## The one thing both reviewers agreed on, and this pass confirms

Neither review found a way for the *agent's* key to move money outside the policy. The
critical paths they found were operator-side (key deletion) and accounting-side (approval
queues, contest counters). That matches the repository's own trust model: the contract
enforces a ledger, and the operator key is the part that is not defended by code.
